# Where Jev can improve Sutura

Date: 2026-10-28. Baseline: `develop` at `969bd68b08c973c3a16f00bb2b67dc19c6300a6d`, `/Users/juan/code/sutura`. This requested assessment follows the [descriptive research](2026-10-28-jev-capabilities-research.md). Recommendations below are hypotheses supported by interface fit and source inspection, not measured performance gains.

## Recommendation

Use Jev for bounded semantic judgments while retaining deterministic control and executable verification. First strengthen the existing audit's evidence and model-version discipline. The highest-value performance experiment is semantic ranking of eligible repair branches; the strongest developer-facing extension is evidence navigation and explanation of unresolved failures. Do not replace the repair generator, execution tests or CI authority with Jev.

Criteria: fewer unsuccessful sandbox branches, lower end-to-end latency and cost per verified repair, preserved repair success and trap rejection, clearer developer actions, bounded maintenance and privacy exposure, and reproducible judgments. Cheap individual API calls do not establish any of these outcomes.

## Performance implications

About 85.9% of recorded v0.4.1 benchmark cost came from sandbox execution (calculated from `docs/demo/sutura-v0.4.1-release-benchmark-evidence.md:44`). Even eliminating all recorded inference cost would save only about 14.1% on that historical workload. That is a cost bound, not a latency bound. Better branch selection could affect the dominant expense, but no current evidence demonstrates that it will.

Jev already batches five questions in one request (`packages/core/src/audit/typesafe-audit.ts:43-83`), so merely adopting [fan-out](https://docs.typesafe.ai/patterns/fan-out) would duplicate existing behavior. Batch new questions only when they share the same necessary state; do not add an unconditional provider call to every deterministic path.

Audit voices currently run sequentially (`packages/core/src/verification/runtime.ts:108-119`). A separately evaluated bounded concurrent schedule could reduce their critical path, but it may spend on optional calls after the primary model would already refuse. This is mostly an orchestration optimization, not a unique Jev capability. Preserve independent budget reservations, deadlines, ordered evidence and replay behavior; compare latency and total spend before choosing it.

## Decision contract for a possible experiment

| Observed condition | Application behavior |
| --- | --- |
| Native policy, identity or execution gate fails | Existing refusal/stop; a model score cannot override it. |
| Eligible branches and enough evidence, with validated ranking signal | Reorder only within the existing permitted frontier and budget. |
| Ambiguous answer, no suitable option, truncated evidence, timeout or provider failure | Preserve existing deterministic ordering; record unavailable/uncertain, never convert failure to a negative answer. |
| Semantic audit concern | Apply only the separately validated veto contract; never grant acceptance. |
| Diagnostic recommendation requires credentials, dispatch, publication or broader scope | Display the evidence and action; preserve the existing authorization boundary. |

Use probabilities directly where relevant. TypeSafe [confidence](https://docs.typesafe.ai/confidence) is a distribution statistic, not a second independent vote. With two Choice options the documented formula makes 0.7 confidence correspond to a top probability of 0.85; the current uncertainty-first policy is therefore not simply a 0.5 green-wash cutoff. Changes to labels, model or question wording invalidate assumptions about old calibration.

A narrower alternative to broad classification replacement is typed recovery-hypothesis selection. Existing hypotheses already use supplied source/signal indices, three intents and controller probes (`packages/core/src/diagnose/hypotheses.ts:55-86`, `:165-245`). Jev could select those bounded options while retaining deterministic fast paths and exact-source grants. Its value depends on how frequently the generative fallback runs. Also, classification currently follows baseline reproduction (`packages/core/src/heal.ts:1098-1116`), so classifier savings cannot be credited with avoiding that initial sandbox cost.

## Alternatives and exclusions

The baseline alternative is no new model: improve explicit evidence presentation, parser coverage or deterministic branch features where those can compute the answer. This costs no provider latency and remains the preferred choice for exact identity, arithmetic, command selection, limits, authorization and hosted CI routing (`docs/ci-routing.md:3-17`, `packages/core/src/llm/routing-policy.ts:129-137`).

Keep the provider-free `assess` path provider-free (`packages/cli/src/assess.ts:47-48`); any semantic assistance should be a separately optional interface. Existing recovery reports already show hypotheses and reasons (`packages/core/src/report/recovery-summary.ts:4-14`), so an evidence navigator must demonstrate utility beyond those reports.

Keep Nemotron for generation and multi-step diagnosis. Jev is not a code generator. Keep executable reproduction for flaky classification and test execution for correctness; a plausibility probability cannot establish either. Defer screenshot-based regression gates: [Images](https://docs.typesafe.ai/images) and [Box](https://docs.typesafe.ai/primitives/box) are explicitly experimental. Defer autoresearch-derived routing until there is adequate labeled outcome data, and do not train or tune on the sealed evaluation split. Do not enable long context by default; [the catalog](https://docs.typesafe.ai/models) warns of latency and accuracy costs.

## Evidence needed to change the recommendation

Compare a fixed baseline with one change at a time on identical case contents, policy, budgets and model versions. Include clean repairs, deceptive patches, unknown failure classes, multi-failure logs, long context, injected instructions, provider failures and option-order perturbations. Separate development data from untouched evaluation data and preserve the existing sealed-corpus controls.

For audit changes measure false refusals, false approvals, abstentions, calibration and skipped rate. For ranking measure verified repair success, attempted branches, sandbox seconds, total cost per successful repair, p50/p95 end-to-end time and false approvals. A cheaper run that gives up earlier is not a gain. For evidence navigation measure whether developers identify the actual cause and next action more accurately and quickly. No such developer study was performed here.

The hypothesis is rejected if semantic ranking costs more than it saves, harms repair coverage, or increases unsafe acceptance; if a parser gives equivalent classification, prefer it. Expand beyond the existing veto only after the comparison supports the intended outcome and the owner accepts the changed role. Public provider cookbook results are examples on other datasets, not Sutura benchmarks.

## Integration constraints

The [complete external source catalog](2026-10-28-jev-source-catalog.md) records all 131 indexed pages and OpenAPI, retrieval date, SDK differences and experimental surfaces. Expanding the current adapter requires typed response validation and replay coverage; adopting the SDK is optional. In particular, the documented JavaScript SDK uses per-attempt timeouts without a total retry budget, unlike the Python defaults, and debug logging can include unredacted request bodies. Preserve Sutura's bounded deadlines, accounting and redaction rather than inheriting defaults. See [SDK configuration](https://docs.typesafe.ai/sdk/javascript/api/interfaces/TypeSafeClientConfig) and [retry policy](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy). New Jev roles need their own explicit budget accounting instead of silently consuming the audit reserve (`packages/core/src/engine/repair-budget.ts:16-25`).
