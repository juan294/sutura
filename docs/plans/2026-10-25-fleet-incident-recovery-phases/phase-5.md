## Product contract and implementation

The initial audience is GitHub Actions projects with supported self-contained Node or Python verification and locked public dependencies. Node 22/24, bounded workspace syntax, supported Python lock/interpreter forms, disabled lifecycle/network behavior and two-file repair bounds must match the shipped runtime (`packages/core/src/runtime/node.ts:43`; `runtime/python.ts:24`; `executor/contree.ts:707`; `engine/repair-targets.ts:15`). Services, private registries, native preparation, unsupported snapshot size and ambiguous polyglot roots are explicit capability gaps. A language match alone is insufficient. Scope support to the selected job, not an entire repository: a project with service-backed integration tests may still have a supported self-contained unit-test job. Say “no application secrets or unsupported native-build/service requirements in the selected job,” not “no secrets anywhere”; provider credentials remain required for live execution.

Before the installation/account-creation instructions, README and user guide must state this supported shape, current ConTree access prerequisite, excluded capabilities and the assessment-first path. The product promise for this cycle is guided setup for assessed repository/job shapes with provider access; do not advertise universal plug-and-play. Retain ConTree as the executor in this plan. No alternative executor's feasibility or security parity is established; replacement requires a separate evidence-backed decision. This positioning correction can be prepared with phase 1's existing-fix documentation and shipped in the first applicable release; documenting the new assess command waits for that command to ship.

1. Add proposed `sutura assess [path] [--json]` as a provider-free, bounded local repository assessment. Read allowlisted manifests, lockfile metadata and workflow definitions as data. Do not execute scripts, read secret values, follow escaping symlinks or scan the home directory. Enumerate truncation/ambiguity; ask only for an unresolved root/runtime or intended capability. Default to one selected root; optional multiple roots are explicit input, not silent workspace discovery. Produce support-by-workflow, evidence stage, uncertainty and a concrete next command even when no repair is possible. Bare CLI and per-command help describe the journey; help must not trigger authentication/network/writes.
2. Add optional selected run/log diagnosis using scoped read access. Reuse the pure phase 3 classification/support contract and phase 4 failure identity, with no live repair. Explain the selected repository/run data access before obtaining it; existing explicit invocation of that scope is sufficient. Native logs are untrusted bounded data. No inference/sandbox account is required for deterministic assessment. Incomplete logs yield unknown, not supported or a guessed source defect.
3. Evolve `init` into prepare/apply with an exact diff and capability manifest. `init --plan` prepares; interactive `init` shows the same plan and can apply once reviewed; noninteractive application requires `--apply` with a matching plan digest. Never upload ambient optional provider keys. Record selected providers, destinations, credential names, actual permissions, cost bounds and retention controls before external processing. Reuse existing repository authentication and customized App wiring; do not assume this owner's branches, RPI installation, CI cadence or local layout. Local file preparation, GitHub configuration and activation are distinct states. Version/document the intentional noninteractive behavior change so old automation receives a migration message rather than a silent new side effect.
4. Persist a minimal versioned local setup receipt with desired-plan digest, completed operations, nonsecret resource identities and next action. Write operation intent before each side effect and mark its receipt afterward. Resume by re-reading live state; do not replay confirmed completed secret uploads or overwrite user edits. A crash after remote secret write but before receipt is pending/unknown because secret-name presence cannot prove value equality. Reconcile provider audit/operation evidence when available; otherwise mark `outcome-unknown`, disclose the ambiguity and prepare an explicit idempotent replacement of the selected credential under the existing scope, without claiming exactly-once mutation or exposing its value. Do not execute that uncertain replacement automatically; present the concrete reconciliation for confirmation before repeating the write. Revalidate credential access with scoped operations only when that access is authorized, rather than printing values or treating names as validity. Readiness stages are `assessed`, `configured`, `activated`, `prepared`, `reproduced`, `native-verified`, `integrated`; unavailable stages stay explicit. Machine output separates operation success from repair outcome: process exit 0 for completed requested assessment (including unsupported verdict), 2 for incomplete requested configuration/readiness, 1 for operational failure. Never call a generated file a ready installation.
5. Make doctor explain each stage and next operation. Accept semantically valid App-token wiring instead of only the literal automatic-token string (`packages/cli/src/doctor.ts:105`). Show native PR-check approval boundaries early; an approved token configuration is not proof of started native CI. Keep `heal`, `verify`, reduced-assurance audit and recorded replay semantics distinct. A bounded first live failure uses an explicit selected run and reviewed provider/cost scope; no automatic paid smoke from init/doctor. Doctor must invoke the shared compatibility assessment and show per-job static verdict (`candidate-supported`, `unsupported`, `unknown`), failure classes covered, missing prerequisites and exact evidence version. Known incompatibility blocks a repair-ready verdict; static success is labeled candidate support and preparation remains unverified until an authorized bounded execution succeeds. Historical failures can expose environment blockers, but do not prove the current checkout fails the same way. No current failure means assessed readiness, not synthetic success.

   Check trigger reachability separately: exact watched workflow identity/name, source events/branches, job conditions, recursion/disable guards and presence on the required default branch. With scoped read access, compare a bounded history of eligible failed source runs against monitor invocations. Report `configured-unexercised`, `observed-delivery`, `missed-eligible-event`, `misconfigured` or `unknown` with the actual observation window. Static reachability cannot promise that CI will fail or that the trigger will ever fire. Healthy CI with zero eligible failures is unexercised, not a broken installation. Unresolved dynamic workflow expressions remain unknown rather than guessed.

   Show configured execution limits and a separate cost estimate only where a dated pricing source and justified token/time/workload assumptions exist. Label measured costs, modeled ranges and enforceable limits distinctly; missing sandbox/runner pricing stays unknown. Existing inference/audit pools (`packages/core/src/engine/repair-budget.ts:1`) are not a cap on total provider and GitHub-runner charges. Display unpriced components before live consent; never report an exact expected attempt cost from static manifests alone. Assessment does not fetch prices or call providers by default.

   For an existing installation, show the last known preparation/reproduction outcome, installed Action identity, observation age and a concrete recovery action when GitHub read access is granted. A developer must be able to obtain this result through their own doctor output and Action summary without access to the maintainer's private collector. Do not infer that they read or understood an existing log merely because it was published.
6. Add proposed `sutura upgrade --plan` and reviewed apply using the same receipt/preview contract, plus documented pause/resume/remove operations. Compute minimal owned changes; preserve custom permissions, App bindings, workflow names and non-Sutura jobs. For receipt-free legacy installations, resolve the exact installed Action/template identity and capture current workflow bytes; infer owned regions only where provable, then save a reviewed baseline before the first upgrade. If the original template/ownership cannot be established, show a proposed resolution diff and recovery command without overwriting custom wiring. Conflicting user edits produce a three-way diff and recovery command, not `init --force` overwrite. Show CLI/package version, installed Action SHA, desired release and capability changes separately. Pause affects future automatic repair admission; diagnosis stays available. Remove only identified Sutura-owned resources after preview; keep user configuration and evidence unless explicitly included. Update install smoke and version-matched help/user/security docs, including stale rebuild and Python statements.

```text
@ adoptRepository(root, capability, priorReceipt) -> readiness
ctx: bounded local data and explicitly scoped remote adapters
pre: selected root and requested operations known
do:
  1. parse compatibility evidence without executing source
  2. compute capability plan and exact operation diff
  3. validate plan digest and authority before each effect
  4. write completed operations and next recovery action
br: unknown or unsupported -> useful diagnosis; selected supported scope -> configure
fail: interruption or drift -> incomplete receipt and resumable preview
```

## Automated acceptance

Add real temporary-repository CLI tests for supported Node, supported Python and unsupported service/native/private dependency profiles; package-script wrappers, valid workspaces and ambiguous polyglot roots; escaped symlinks, hostile manifest text, truncated scans and no-current-failure cases. Assert zero shell/provider/network calls for default assess and help, zero unselected secret uploads, exact explicit remote scope, and no cross-root reads. Stage claims require their own evidence. Add local/hosted parity fixtures tied to installed/target contract versions, a newer CLI assessing an older Action, known-preparation refusal, and static-pass/execution-fail cases. Trigger fixtures distinguish all-green/no-opportunity from renamed/unwatched workflow, mismatched branch/condition, absent default-branch activation, eligible run with no monitor, incomplete run history and dynamic expression uncertainty. Cost fixtures distinguish configured inference limit, modeled range, unknown execution charges and post-run measurement; no known subset is labeled total cost. Scope scanning overhead with fixed file/byte bounds and deterministic timeouts; report bounds in output.

Installer fault injection before and after every side effect, including remote success followed by lost receipt, must leave a recoverable receipt. Resume with restored access or edited workflow without duplicating changes. Test stale plan digests, removed permissions, user cancellation, scoped credential validation failures, custom App tokens, token-created PR pending approval, default-branch activation absent, partial setup exit codes and schema backward compatibility. Test a receipt-free v0.3.9 workflow with custom App token, permissions and unrelated jobs, including initial baseline capture and subsequent resume. Test upgrade preserving customization, conflict resolution, pause/resume, removal preserving unrelated jobs and evidence. Compare actual generated workflow/event semantics and doctor interpretation, not just matching strings. Root/package Action metadata and phase 6 generator integration are tested again before release.
