# Phase 2 — Compatibility pilot and early activation

Parent: [fleet incident recovery](../2026-10-25-fleet-incident-recovery.md). Entry: phase 1 known-fix subset accepted, exact candidate local gates complete, and each external action specifically authorized. No dependency on phases 3–6. The private annex names the two fixture/runtime-blocked pilot consumers and the App-wiring target.

## Delivery contract

1. Refresh the integration/default branches, deployed pins and configuration metadata. Inspect the candidate's full diff from the installed stable version, including generated bundles and deployment triggers. The first candidate reuses existing fixture handling and Node-range corrections (`packages/core/src/security/snapshot-inputs.ts:12`; `packages/core/src/runtime/node.ts:10`). Do not cherry-pick blindly across a large unreleased diff: either qualify the complete immutable candidate or prepare a minimal compatibility candidate with its actual dependency closure and full gates.
2. Preserve existing monitor/job conditions, App-token wiring, watched names and protected CI routing. Prepare minimal pin/grouping patches and the missing-App packet from phase 1, with exact prior workflow bytes, native obligations and rollback. A diagnosis-only oversized consumer retains visible coverage but is excluded from automatic repair/spending through a protected explicit policy. Before the new inspect mode ships, use existing collector coverage plus a documented repair-admission exclusion; never invent an unsupported action input. If no current exclusion can preserve diagnostic coverage without execution, prepare that narrow guard with local tests as part of phase 1 rather than enabling an unsupported path.
3. Publish only the completed approved candidate and approved consumer patches; inspect every expected exact-SHA native workflow. The explicit-SHA path already exists (`packages/cli/src/release.ts:21`). A candidate pin does not require falsely labeling an unshipped npm version stable. Default-branch activation follows each consumer's actual topology, including any separately authorized production/default-branch merge. Execute the approved App packet via CLI and verify scoped token/readback without exposing values.
4. Observe 72 hours for safety and delivery drift using existing collector evidence. Zero eligible failures means compatibility installed but stop removal unexercised. Captured RED/GREEN regression, exact-candidate full checks, default-branch pin readback and no observed safety regression suffice to distribute the same compatibility subset to additional approved consumers; do not require an organic repair to ship those already-evidenced fixes. Each consumer still needs local gates, specific authority and exact hosted readback.
5. On the next eligible event, require evidence that the previously failing stage actually passed before marking its stop cause removed. A different earlier exception or a never-entered stage is not proof. An unrelated later stop does not invalidate the passed-stage result, but it also does not count as a repair. Stable reliability/adoption release and organic repair proof retain phases 7/8 gates.

## Automated acceptance

Captured regression cases fail under the old compatibility behavior and pass under the candidate. Preserve rejection tests for unsafe inputs and unsupported Node ranges. Candidate installation/package tests, bundle checks, existing protected native obligations and all parent local gates pass. Grouped-update fixtures cover the actual multi-action update, not merely YAML key presence. App correction and diagnostic-only policy fixtures prove later eligible work can proceed and excluded cases consume no provider work.

Test the pilot evaluator with: stage passed then later unrelated failure; earlier stop hiding the stage; zero events; incomplete collection; wrong pin; missing required job; no default-branch activation; candidate rollback. Only the first can prove stop removal. No case labels an installed candidate an organic repair.

## Stuck states, manual acceptance and handoff

Missing authority leaves a concrete prepared packet and pending activation state. Failed native CI stops expansion; retain logs, fix locally, complete gates and request the next remote action under push accountability. No automatic rerun/fix-and-repush loop. No event ends the fixed observation window as unexercised and establishes a next-event resumption condition. The local correctness phases may proceed once this disposition is recorded; empirical waiting is not a new infrastructure dependency.

The owner reviews candidate scope, rollback, installed versus exercised evidence and remaining failures. Delivery of the compatibility subset does not fulfill the whole plan. Local per-consumer preparation is `[batch-eligible]` with disjoint worktrees and one integration owner; all checks and hosted activations remain sequential. Handoff includes exact candidate/install identities, action receipts, stage evidence, unavailable data and the remaining phase 3 register.
