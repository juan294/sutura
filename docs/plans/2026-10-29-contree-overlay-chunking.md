## Objective

A repository whose overlay archive is larger than the provider boundary (observed between 132,956,160 and 134,963,200 bytes) completes the repository-overlay step in local tests with the same resulting workspace, the same prepared dependencies and the same Git baseline as a small repository. Repositories under the boundary keep byte-identical provider requests.

## Design decisions

**D1 (chosen): split the repository overlay into sequential chunks inside `ContreeExecutor.snapshot`.** Each chunk is a tar of at most `overlayChunkBytes` (default 64 MiB), uploaded and extracted by its own instance on the image produced by the previous chunk. The last chunk's image is returned. No change to the `Executor` interface, to callers or to the replay `snapshot` record. 64 MiB is half the lowest observed failing archive. It also keeps the peak of one instance (tar plus extracted files, about twice the chunk) near 128 MiB, which is half of the lowest failing doubled size under the layer-bytes hypothesis. Both E3 hypotheses are covered, so the plan does not depend on resolving which provider limit applies.

Rejected alternatives:

- **Exclude more paths (for example `docs/agents/**`).** Changes the files that repository tests and verification see, depends on one project's layout, and recurs when another directory grows (Sutura's own repository crossed the boundary at 134,963,200 bytes with no evidence directory). Retained as the existing narrow rule at `contree.ts:1004`.
- **Compress the tar.** The gain on a PNG-heavy tree is unmeasured, extracted bytes stay the same, and every repository's request bytes change, which breaks hash-pinned fixtures.
- **Lower the archive cap and fail early.** Names the problem sooner but leaves Spoken Letter and Sutura's own dogfood unrepaired.
- **Send `resources_limits.max_layer_bytes`.** The default is 12 GiB, about 80 times the failing archive, so the field is not shown to be the limit.

**D2: byte-identical single-chunk path.** When the planned archive fits in one chunk the executor issues exactly today's requests, command string and file map. This keeps the captured compatibility tests, replay fixtures and every repository under the boundary unchanged.

**D3: complete manifest in the final image.** Multi-chunk runs inject the full overlay manifest at `/tmp/sutura-repository-overlay.manifest` with the first chunk, and give each chunk a separate members file for collision and symlink validation. Chunks after the first leave the manifest in place. This satisfies E5 without touching `heal.ts`.

**D4: configurable budget, no new Action input.** `ContreeExecutorConfig.overlayChunkBytes` (positive safe integer, default 64 MiB) exists so tests can use small values. The Action and CLI do not expose it, and no environment variable reads it.

**D5: a single file larger than the budget is refused before any upload**, with the path and size in the message. The largest tracked file in the sampled repositories is about 4 MiB, so this is a guard, not an expected path.

**D6: failure context for multi-chunk runs.** If a chunk instance fails, the `ContreeError` is rethrown with the same `status`, `body`, `code`, `stage`, `details` and `providerTerminal` and with the message suffix `(repository overlay chunk K of N, B archive bytes)`. Single-chunk failures keep today's message (D2). The typed ENOSPC classification keys on the provider's error string and does not change (`contree.ts:1431-1439`).

**D7: live proof is out of scope.** Acceptance is local. Whether the hosted provider accepts chunked overlays is unproven until a separately authorized dispatch. The plan states this in the handoff and the evaluation limitation text, and does not claim hosted recovery.

## Behavioral oracles (executable)

- **O-IDENTITY:** the existing tests that assert upload bodies, the command string and the file map for a small repository (`contree.test.ts:752`, `contree.test.ts:1336-1420`, `snapshot-compatibility.captured.test.ts`) pass unchanged. A new test asserts the request sequence for a one-chunk overlay is deep-equal to the pre-change sequence.
- **O-SIZE:** a synthetic tree with the Spoken Letter profile scaled by a small `overlayChunkBytes` (same file count and size distribution: 5,790 files, 145,798,039 bytes at scale 1; scaled to 1 MiB budget in the test) yields N chunks. Each uploaded tar is at most the budget, the members files partition the file list exactly (no file missing or repeated), and the full manifest equals the single-archive manifest.
- **O-PEAK:** for every chunk instance, tar bytes plus the sum of its member file bytes is at most twice the budget.
- **O-CHAIN:** each chunk instance's `image` is the previous instance's `result_image_uuid`; the executor returns the last result image; a failure on chunk K stops the chain and never starts chunk K+1.
- **O-WORKSPACE:** extracting the chunk tars in order with the real shell command into a directory that already holds prepared dependencies reproduces the file set of a single-archive extraction, preserves `node_modules`, and leaves a manifest listing every path (the existing shell contract fixture extended to three chunks).
- **O-BASELINE:** the Git baseline command from `heal.ts` run over the multi-chunk result adds every manifest path (`git ls-files` count equals manifest entries).
- **O-REFUSE:** symlink-parent, symlink-destination and preparation-collision refusals still happen before extraction of the chunk they affect, in a later chunk as well as the first.
- **O-GUARD:** a file larger than the budget is refused with its path and size before any file upload request.
- **O-ERROR:** a provider `FAILED` ENOSPC on chunk 2 of 3 yields a `ContreeError` with `code: 'provider-disk-exhausted'`, `stage: 'provider-operation'`, the original `details` and a message containing the original provider text plus `chunk 2 of 3`.
